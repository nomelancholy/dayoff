# 운영 서버 로그 확인

## 재고 갱신 및 배포 중 접속 오류

- 상품 저장 성공 시 서버 응답을 관리자 목록·상품 목록·ID/slug 상세 캐시에 즉시 반영하고
  관련 목록과 장바구니를 다시 조회하도록 표시합니다. 브라우저 강력 새로고침은 필요 없습니다.
  회귀 검증: Node 22.6 이상에서 `node --experimental-strip-types --test tests/product-cache.test.mjs`.
- 2026-10-16 00:18:01 KST의 Cloudflare 521은 배포의 웹 컨테이너 교체 구간
  (00:17:59~00:18:16 KST)과 일치했습니다. 521은 원본 서버 연결 거부이며,
  클라이언트 캐시 문제와 별개입니다.
- 배포는 DB → API 준비 확인 → 새 Nginx 설정/인증서 검사 → 웹 교체 → HTTP 확인 순으로
  진행합니다. DB/API를 준비하는 동안 기존 웹 컨테이너를 유지하고 중복 배포는 직렬화합니다.
  API 준비 실패 시 기존 웹을 교체하지 않습니다.
- Nginx는 Docker DNS를 다시 조회하므로 API 재생성에 따른 IP 변경을 따라갑니다.
  SPA HTML은 저장하지 않아 새 배포 이후 이전 JS 파일을 계속 참조하는 상황을 줄입니다.
- **현재 단일 웹 컨테이너 교체 순간에는 짧은 접속 중단이 남습니다.** 완전한 무중단 배포는
  고정된 외부 프록시/로드밸런서 뒤에서 두 릴리스를 겹쳐 실행하는 별도 전환 구조가 필요합니다.
  API 교체 중에는 API 요청이 일시 실패할 수 있습니다. 헬스 체크는 기동 확인이며 자동 롤백이 아닙니다.
- `/healthz`는 웹 프로세스, API 컨테이너의 `/` 체크는 API 기동 상태를 확인합니다.
  배포 마지막 `/shop/products` 검사는 웹 → API → DB 경로까지 확인합니다.

## 로그 읽기

운영 서버에서 프로젝트 디렉터리로 이동한 뒤 아래 명령을 실행합니다.

```sh
./deploy/api-logs.sh
```

기본적으로 API 서버의 최근 200줄을 출력하고 새 로그를 계속 표시합니다. 종료는
`Ctrl+C`입니다. 더 많은 로그가 필요하면 다음과 같이 실행합니다.

```sh
LOG_TAIL=1000 ./deploy/api-logs.sh
```

스크립트를 사용하지 않을 때의 동일한 명령은 다음과 같습니다.

```sh
docker compose -f docker-compose.prod.yml --env-file .env.deploy \
  logs --tail=200 -f api
```

HTTP 500 오류는 요청 방식, 쿼리 문자열을 제외한 요청 경로, 오류 메시지와 스택을
API 컨테이너 로그에 기록합니다. 요청 본문과 인증 헤더는 기록하지 않습니다.

API 로그는 컨테이너별 최대 10MB 파일 5개로 순환 보관됩니다.

Postgres와 Nginx 로그도 동일하게 최대 10MB 파일 5개로 순환 보관됩니다. 배포
워크플로는 새 이미지를 받기 전후에 사용하지 않는 Docker 이미지와 빌드 캐시를
정리하며, 데이터 볼륨은 삭제하지 않습니다.

## 이미지 저장소

DigitalOcean Spaces 환경변수, 설정 점검, 기존 이미지 이전 절차는
[`SPACES_SETUP.md`](./SPACES_SETUP.md)를 참고합니다. 이전이 끝나고 사이트에서

## 네이버페이

주문형 인증값, 주문관리·재고 동기화 준비, 검수 및 비상 비활성화 절차는
[`NAVER_PAY_SETUP.md`](./NAVER_PAY_SETUP.md)를 참고합니다.

검수는 **운영 사이트에서 검수 전용 일반 회원 권한**으로 진행합니다.
새 API/Web 이미지 배포 후 운영 호스트에서 `sh deploy/setup-npay-review.sh`를 실행하면
운영 DB 계정 생성, 검수 전용 노출 설정, API 컨테이너 재생성을 처리합니다.
운영 서버는 `NODE_ENV=production`을 유지하고 네이버페이만 `NAVER_ORDER_MODE=test`로 연결합니다.
운영 로그인·일반 방문자 비노출·전체 상품·장바구니·XML을 확인하기 전에는 검수 준비 완료로 보고하지 않습니다.

## 주문·상품·쿠폰 운영 참고

관리자 화면에서 헷갈릴 수 있는 서버 동작을 정리합니다.

- **상품 삭제**: 주문 이력이 있는 상품은 주문 내역(상품명·이미지·옵션) 보존을 위해 DB에서
  지우지 않고 숨김 처리합니다(`is_active=false`, slug 뒤에 `--deleted-…` 추가, 카테고리 연결 해제).
  쇼핑몰·관리자 목록에서는 사라지고 같은 slug로 새 상품을 등록할 수 있습니다.
  주문 이력이 없는 상품은 이미지 파일까지 완전히 삭제합니다.
- **주문 배송지**: 결제 준비 시점의 배송지를 주문에 고정합니다. 고객이 이후 주소록을 수정·삭제해도
  이미 접수된 주문의 배송지는 바뀌지 않으므로, 배송지 변경 요청은 별도로 확인해 처리해야 합니다.
- **pending 일괄 삭제**: 최근 1시간 안에 만들어진 초안(결제창이 열려 있을 수 있음)과
  네이버페이 결제번호가 연결된 pending 주문은 지우지 않습니다. 결제번호가 연결된 채 pending으로
  남은 주문은 승인 후 확정·자동취소가 모두 실패한 건이므로 API 로그와 네이버페이센터에서
  결제 상태를 확인해야 합니다.
- **쿠폰 기간**: 날짜만 입력하면 한국 시간 기준 시작일 00:00부터 종료일 23:59:59까지 유효합니다.
- **쿠폰 사용**: 같은 쿠폰은 회원당 한 번만 사용할 수 있고, 다시 지급하면 지급한 만큼 다시 쓸 수 있습니다.
  주문이 취소되면 사용 처리가 되돌아갑니다.
- **쿠폰 지급**: 지급하면 해당 회원에게 쿠폰 코드와 사용 조건을 담은 안내 메일을 보냅니다
  (`RESEND_API_KEY` 미설정 시 생략). 쿠폰을 삭제하면 지급된 쿠폰도 함께 회수되고,
  이미 사용된 주문의 할인 금액은 그대로 유지됩니다.
- **회원 탈퇴**: 결제 완료 후 발송 전인 주문이 있으면 탈퇴가 막힙니다. (주문이 함께 삭제되어
  환불도 발송도 되지 않는 상황 방지)

## DB 마이그레이션 백업

API 교체 직전에 운영 호스트의 `backups/pre-deploy-<UTC시각>-<커밋>.dump`에 PostgreSQL custom dump를 저장하고 `pg_restore --list`로 읽을 수 있는지 검사합니다. 백업 실패 시 API를 교체하지 않습니다. 백업 파일은 호스트에만 보관하며 배포 로그에는 내용이나 인증값을 출력하지 않습니다. 별도 보관 정책에 따라 외부 백업 및 보존 기간을 관리하세요.
